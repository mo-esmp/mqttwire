# .NET 11 against .NET 10

Issue #47 gives both packages a `net11.0` build beside the `net10.0` one
([the design](../specs/2026-11-27-net11-target-design.md)). This report measures what that
means for speed and memory: the same MqttWire on the two runtimes, and the `net10.0` build
before and after the change.

## 1. Summary

- **MqttWire allocates the same on both runtimes.** Every microbenchmark allocates what it did:
  nothing on the codec, the receive paths and the delivery encoding, 32 B for an awaited QoS 1
  publish. The allocation tests pass on both without a change. End to end, bytes per operation
  agree within 0.5%, except the blocking round trip, which is 2.5% higher on .NET 11 for the
  whole process, MQTTnet's broker included.
- **Speed: no difference that the measurements can hold on to, with two exceptions.** Encoding
  a CONNACK with user properties is about 11% faster on .NET 11 in both runs, and an awaited QoS
  1 publish on the in-memory link is 19 to 35% faster in four pairs of four. Everything else is
  inside what the same build shows against itself from one benchmark process to another. Two
  results that looked like a difference at first were not (section 4).
- **An idle connection costs about 2,000 bytes more on .NET 11, and none of it is MqttWire's.**
  The bare ASP.NET Core WebSocket that the benchmark of design 6.14 calls the floor takes about
  10,750 live managed bytes per connection on .NET 10 and about 12,770 on .NET 11. MqttWire adds
  583 to 711 bytes to it on .NET 10 and 602 to 706 on .NET 11, so the target of "floor + 1 KB"
  is met on both. The heap dumps put the difference in Kestrel's two pipes per connection
  (about 1,340 bytes) and in how the .NET 11 framework keeps its own suspended `async` methods
  (about 650 bytes). MqttWire's own objects are the same 591 bytes on both.
- **The `net10.0` build is not the same assembly as before,** because the .NET 11 SDK's compiler
  builds it now: 12 of the 702 methods of `MqttWire` and 4 of the 525 of `MqttWire.Server` have
  different IL, nearly all a few bytes shorter. Measured before and after on .NET 10, nothing is
  slower and nothing allocates more; `ReceiveQoS0` is 8 and 10% faster in the two pairs.

So a host can move to .NET 11 without a cost in MqttWire, and should know that the framework
beneath it currently holds about 19% more memory for an idle WebSocket connection.

## 2. What was measured

All on 2026-11-27, between 18:36 and 20:05, on one machine: Windows 11 Pro 10.0.26200 on arm64,
a virtual machine (Parallels) on Apple Silicon with 10 logical processors; .NET SDK 11.0.100;
the runtimes and ASP.NET Core 10.0.15 and 11.0.0; BenchmarkDotNet 0.15.8, default job; Release
builds; nothing else at work on the machine during a measurement. The VM is noisy, and no number
here is good to more than a few percent.

The code is `main` at 6bd7563 with the change for #47, which changes no source file of either
package. "Before" in section 6 is `main` at 6bd7563 itself, built by the .NET 10 SDK (10.0.404).

| What | Instrument | How the two sides were kept comparable |
|---|---|---|
| The codec, the client on an in-memory link and over a WebSocket on pipes, the server's delivery encoding | `bench/MqttWire.Microbench --both-runtimes` | One BenchmarkDotNet run with a job for each runtime; two full runs, two more of the two noisiest benchmarks, and a fifth of six benchmarks with another filter |
| The client end to end, QoS 1 over a loopback WebSocket to MQTTnet's broker | `bench/MqttWire.Probe` | The probe's `net10.0` and `net11.0` builds run in turns: 10, 11, 11, 10, 10, 11 |
| The server's memory per idle connection (design 6.14) | `bench/MqttWire.Bench run` | The two builds in turns, in the same order; then one run of each with heap dumps |
| The `net10.0` build before and after | The probe with `before`, and `bench/MqttWire.Microbench` in a worktree of `main` and in the branch | The probe interleaves the two clients in one process; the BenchmarkDotNet runs alternate, before, after, before, after |

A runtime difference and a build difference are not separated in the first three: the `net10.0`
build runs on .NET 10 and the `net11.0` build on .NET 11, which is what an application gets. The
two builds of `MqttWire` have the same IL in every method. Those of `MqttWire.Server` differ in
four methods, all generated by the logging source generator of each framework
(`ServerLog.__…Struct.get_Item`), which run only when a log entry is read.

## 4. What the microbenchmarks do and do not show

**Two results were not what they looked like.**

`EncodePublishLongTopic` was 0.62 and 0.75 of its .NET 10 time on .NET 11. But the same
`net10.0` build on the same .NET 10 runs it in 20.2 to 21.9 ns in four other measurements
(section 6, and the run below), not in the 32 to 35 ns of the two runs above. What differs
between those measurements is only which benchmarks are in the run, and so how the benchmark
process is laid out. The benchmark copies a topic of 256 bytes, and a copy is sensitive to
where its buffers happen to lie.

`ReceiveQoS0OverWebSocket` was slower on .NET 11 in four runs, by 7 to 40%, and faster in the
fifth, by 18%, with a spread inside each run of up to about 30%. It wakes a waiting read loop for
every message, so it measures the scheduler of a virtual machine as much as the code.

A fifth run with only six benchmarks in it, to check both:

| Benchmark | .NET 10 | .NET 11 | 11/10 |
|---|---:|---:|---:|
| `EncodePublishLongTopic` | 21.93 ± 0.06 | 20.39 ± 0.13 | 0.93 |
| `DecodePublishQoS1` | 8.84 ± 0.08 | 7.99 ± 0.02 | 0.90 |
| `ReceiveQoS0` | 63.82 ± 0.65 | 65.19 ± 0.47 | 1.02 |
| `ReceiveQoS1` | 100.83 ± 0.59 | 102.69 ± 0.22 | 1.02 |
| `ReceiveQoS0OverWebSocket` | 2,270.0 ± 158.4 | 1,872.0 ± 202.2 | 0.82 |

**How much the same build moves by itself.** Over all the measurements of the `net10.0` build
on .NET 10 in this report (the three two-runtime runs, the two "after" runs of section 6 and a
single-job run), `ReceiveQoS0` is 60.9 to 69.3 ns, `ReceiveQoS1` 100.8 to 106.6 ns and
`DecodePublishQoS1` 8.6 to 8.9 ns. A ratio between the runtimes inside such a band says
nothing. That covers the receive paths (1.01 to 1.08), `DecodeSubscribe`, `FrameStream`,
`PublishQoS0` and the delivery encoding. `DecodePublishQoS1` on .NET 11 was 7.9, 11.1 and 8.0
ns in its three runs: it moves more from run to run than from runtime to runtime.

**What is left.**

- `EncodeConnAckUserProperties`: 0.88 and 0.89, with .NET 10 at 1,079 to 1,112 ns in all six of
  its measurements (section 6 included) and .NET 11 at 948 and 991 ns. About 11% faster on
  .NET 11.
- `PublishQoS1AwaitAck`: 0.65 to 0.81 in four pairs; .NET 10 is 2,100 to 3,007 ns over all its
  measurements and .NET 11 1,524 to 2,357 ns. Faster on .NET 11, by an amount this machine
  cannot fix. The benchmark resumes an awaiting caller from another task. The .NET 11 runtime
  notes name a change on that path (a continuation no longer captures and restores an execution
  context that holds nothing); whether that is the cause was not checked.
- `ReceiveQoS1` is the one path that was slower on .NET 11 in all three pairs: by 2, 5 and 8%,
  or 2 to 8 ns for a received QoS 1 message. It is inside the band above, so it is not shown to
  be real, and not shown to be nothing.

### Who owns the 2,000 bytes

One more run of each build with heap dumps (`run --dumps`, `dotnet-gcdump` 10.0.750501) of
MqttWire's server, idle, at 3,000 and at 12,000 connections. Per connection is the slope, by
type. The dumps' totals are 11,313 bytes per connection on .NET 10 and 13,364 on .NET 11, a
difference of 2,051; the server's own measurement in those runs was 11,335 and 13,387.

| | .NET 10 | .NET 11 | Difference |
|---|---:|---:|---:|
| The pipes: `Pipe`, `BufferSegment`, and what holds the pipe's spare segments | 936 B in 7 objects | 2,280 B in 11 objects | +1,344 |
| Suspended `async` methods of Kestrel | 1,064 B in 6 objects | about 1,720 B in 18 objects | about +656 |
| MqttWire's own types | 591 B | 591 B | 0 |
| Everything else | | | about +51 |

**The pipes.** A connection has two (`System.IO.Pipelines.Pipe`, twice per connection on both),
which Kestrel's socket transport reads into and writes from. On .NET 10 each holds its spare
segments in a small array of structs (`SegmentAsValueType[]`, 168 bytes for three arrays per
connection). On .NET 11 each has a `SingleProducerSingleConsumerQueue<BufferSegment>` (32 bytes)
with a queue segment (`Segment<BufferSegment>`, 424 bytes) and a `BufferSegment[]` (280 bytes):
1,472 bytes per connection, with 56 bytes of the old arrays left. That reading is from the type
names and sizes in the dumps; the .NET source was not consulted.

**Suspended `async` methods.** On .NET 10, six state-machine boxes of Kestrel are parked for an
idle connection (`SocketConnection.DoSend` and `DoReceive`, `KestrelConnection.ExecuteAsync`,
`HttpConnection.ProcessRequestsAsync`, and `HttpProtocol.ProcessRequestsAsync` and
`ProcessRequests`): 1,064 bytes. ASP.NET Core 11 is compiled with runtime-async, and the same
methods are held as four `RuntimeAsyncTask` (288 bytes), four `Action` (224), two
`ValueTaskSourceContinuation` (144), two `RuntimeAsyncTaskContinuation` (144) and six
`Continuation` objects. `dotnet-gcdump` does not report a usable size for the `Continuation`
objects, which vary in size; taken as what is left of the dump's total, they are about 920
bytes, or about 150 each.

**MqttWire.** The same six rows as in
[the idle-memory report](2026-11-idle-memory.md) (section 5), with the same sizes on both
runtimes: `MqttWireConnection` 232, the state machine of its run 152, the state machine of the
link's parked wait 128, `WebSocketLink` 32, its entry in the client-id table 36 and its slot in
the array the sweep walks 11. Its `net11.0` build keeps the compiler's state machines
([the design](../specs/2026-11-27-net11-target-design.md), section 3), so nothing of it moved.

Nothing in this is MqttWire's to change: the pipes and the request loop belong to Kestrel, and
a host cannot turn runtime-async off inside the shared framework. It does add to what issue #41
is about: what Kestrel and .NET cost per connection was about 94% of an idle connection's total
on .NET 10 already (10,750 of 11,380 bytes), and it is 2,000 bytes more now.

## 7. What this does not show

- **One machine,** a virtual one, on arm64 and Windows. Linux and x64 were not measured; CI runs
  the tests on Linux on both runtimes, and no benchmark.
- **.NET 11.0.0,** the first release. A servicing release may change the floor in either
  direction; the benchmark of design 6.14 is the way to see it.
- **Blazor WebAssembly.** The client's `net11.0` build is built into the sample's WebAssembly
  client by CI, and was not measured or run in a browser for this report.
- **TLS** in the idle-memory benchmark (`run --tls`) on .NET 11.
- **Heap dumps of more than one run,** and of the bare floor: the attribution is of MqttWire's
  server, idle, in one run of each runtime.
- **The comparisons with MQTTnet** in BenchmarkDotNet (`ClientComparisonBenchmarks`,
  `CodecComparisonBenchmarks`); the probe covers the client's side of them.
- **Where the 58 bytes of the blocking round trip come from** (section 5).

## 8. Running it

```
dotnet build -c Release
dotnet run -c Release -f net10.0 --no-build --project bench/MqttWire.Microbench -- --both-runtimes --filter "*.CodecBenchmarks.*" "*ClientBenchmarks*" "*DeliveryEncodingBenchmarks*"
dotnet bench/MqttWire.Probe/bin/Release/net10.0/MqttWire.Probe.dll
dotnet bench/MqttWire.Probe/bin/Release/net11.0/MqttWire.Probe.dll
dotnet run -c Release -f net10.0 --no-build --project bench/MqttWire.Bench -- run
dotnet run -c Release -f net11.0 --no-build --project bench/MqttWire.Bench -- run
```

The second command takes about 16 minutes, each probe about 20 seconds and each idle-memory run
about two minutes. `--both-runtimes` must be started on .NET 10 (`-f net10.0`): BenchmarkDotNet
0.15.8 does not know .NET 11, and the program makes the two jobs itself. `"*ClientBenchmarks*"`
takes `ClientBenchmarks` and `WebSocketClientBenchmarks` and leaves the comparisons with MQTTnet
out. For the before and after of section 6, see the remarks of `bench/MqttWire.Probe/Program.cs`.
